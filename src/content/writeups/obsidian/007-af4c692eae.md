## Reconnaissance

La première étape consiste à vérifier que la cible répond sur le réseau.

```bash
ping 172.20.6.26
```

La machine répond correctement, je passe donc à l'énumération des ports.

```bash
nmap -Pn --disable-arp-ping --min-rate 5000 172.20.6.26
```

Ports intéressants découverts :

```text
135/tcp   open  msrpc
139/tcp   open  netbios-ssn
445/tcp   open  microsoft-ds
3389/tcp  open  ms-wbt-server
5985/tcp  open  wsman
```

La présence de `3389/tcp` indique que **RDP (Remote Desktop Protocol)** est disponible.

Je poursuis avec la détection des versions et les scripts Nmap par défaut :

```bash
nmap -Pn --disable-arp-ping --min-rate 5000 172.20.6.26 -sV -sC
```

Le scan retourne notamment :

```text
3389/tcp open  ms-wbt-server Microsoft Terminal Services

ssl-cert:
  Subject: commonName=WIN-B9266PTLH5T

rdp-ntlm-info:
  Target_Name: WIN-B9266PTLH5T
  NetBIOS_Computer_Name: WIN-B9266PTLH5T
  DNS_Computer_Name: WIN-B9266PTLH5T
  Product_Version: 10.0.17763
```

Le hostname peut donc être identifié directement grâce aux informations exposées par RDP :

```text
WIN-B9266PTLH5T
```

Une autre méthode possible est d'interroger NetBIOS :

```bash
nmblookup -A 172.20.6.26
```

> Lors de mon premier essai, j'avais lancé `nmblookup 172.20.6.26`, ce qui n'est pas la bonne syntaxe pour rechercher le nom NetBIOS à partir d'une adresse IP. L'option `-A` est nécessaire dans ce cas.

## Identification de l'OS

J'ai également utilisé la détection d'OS de Nmap :

```bash
nmap -Pn --disable-arp-ping --min-rate 5000 172.20.6.26 -O
```

Résultat :

```text
Running: Microsoft Windows 2019
OS details: Microsoft Windows Server 2019
```

Cela indique que la cible fonctionne sous **Windows Server 2019**.

## Accès RDP

Le compte Windows généralement le plus privilégié localement est :

```text
Administrator
```

Une première tentative avec le mot de passe `Administrator` échoue.

```bash
xfreerdp /v:172.20.6.26 /u:Administrator /p:Administrator
```

Je relance ensuite FreeRDP sans fournir de mot de passe sur la ligne de commande :

```bash
xfreerdp /v:172.20.6.26 /u:Administrator
```

FreeRDP demande alors les informations d'authentification. En laissant le mot de passe vide, la connexion est acceptée.

La machine autorise donc une connexion RDP au compte `Administrator` **sans mot de passe**, ce qui constitue une mauvaise configuration critique.

```text
RDP = Remote Desktop Protocol
```

## Énumération locale Windows

Une fois connecté à la machine, je vérifie les informations du système.

### Version Windows

La commande PowerShell utilisée pour récupérer précisément `WindowsVersion` est :

```powershell
Get-ComputerInfo | Select-Object WindowsVersion
```

Résultat :

```text
WindowsVersion
--------------
1809
```

La réponse attendue est donc :

```text
1809
```

À ne pas confondre avec :

```text
Windows Server 2019  -> nom commercial de l'OS
1809                 -> WindowsVersion
17763                -> numéro de build
10.0.17763           -> version complète du système
```

---

### Recherche du dossier suspect

Pour afficher le contenu de `C:\` :

```powershell
Get-ChildItem C:\
```

ou simplement :

```powershell
dir C:\
```

On remarque un dossier inhabituel :

```text
C:\junk
```

Le dossier suspect est donc :

```text
junk
```

---

### Propriétaire du dossier `junk`

Dans l'interface graphique Windows, le propriétaire peut être trouvé avec :

```text
junk
→ Properties
→ Security
→ Advanced
→ Owner
```

Le propriétaire observé est :

```text
spy7
```

L'équivalent PowerShell, plus rapide lors d'une énumération en ligne de commande, est :

```powershell
(Get-Acl C:\junk).Owner
```

On peut aussi afficher les informations de sécurité plus largement :

```powershell
Get-Acl C:\junk | Format-List
```

`Get-Acl` récupère le **security descriptor** du dossier, dont le champ `Owner` indique le propriétaire.

## Ce qu'il fallait retenir

### RDP

RDP est le protocole Microsoft permettant d'utiliser graphiquement une machine Windows distante. Il utilise généralement :

```text
TCP/3389
```

Un service RDP exposé peut également divulguer des informations avant authentification, par exemple :

- hostname ;
- nom NetBIOS ;
- version Windows ;
- certificat TLS ;
- informations NTLM.

C'est exactement ce qui s'est produit avec le script Nmap `rdp-ntlm-info`.

### Nmap : ne pas s'arrêter aux ports

Le premier scan indiquait seulement :

```text
3389/tcp open ms-wbt-server
```

Mais l'ajout de :

```bash
-sV -sC
```

a permis de récupérer beaucoup plus d'informations, notamment le hostname et la version du système.

La logique à retenir est donc :

```text
Découverte du port
→ identification du service
→ scripts / énumération spécifique au service
→ informations supplémentaires
```

### Windows CLI

Les équivalents PowerShell utiles rencontrés dans cette machine sont :

```powershell
hostname
Get-ComputerInfo | Select-Object WindowsVersion
Get-ChildItem C:\
(Get-Acl C:\junk).Owner
```

L'objectif est progressivement de pouvoir effectuer ce type d'énumération sans dépendre de l'interface graphique.

## Erreurs et fausses pistes utiles

### Reverse DNS sans résultat

```bash
nslookup 172.20.6.26
```

retournait :

```text
NXDOMAIN
```

Cela signifie simplement qu'aucun enregistrement PTR exploitable n'était disponible. Cela ne signifie pas que le hostname ne peut pas être récupéré autrement.

Ici, RDP fournissait directement l'information.

### Mauvaise syntaxe avec `nmblookup`

Commande essayée :

```bash
nmblookup 172.20.6.26
```

Pour rechercher le nom NetBIOS depuis une adresse IP, il fallait utiliser :

```bash
nmblookup -A 172.20.6.26
```

### Erreur de syntaxe Nmap

Cette commande :

```bash
nmap ... - O
```

est incorrecte, car `-O` doit être écrit sans espace :

```bash
nmap ... -O
```

Une simple erreur de syntaxe peut donc complètement changer l'interprétation des arguments par un programme.

## Conclusion

Cette machine était principalement un exercice d'introduction à **RDP et à l'énumération Windows**.

Le point central n'était pas seulement de se connecter à la machine, mais de comprendre que plusieurs informations importantes pouvaient déjà être récupérées à distance grâce à l'énumération du service RDP.

La mauvaise configuration principale était l'accès RDP au compte `Administrator` sans mot de passe. Une fois connecté, l'énumération locale a permis d'identifier la version Windows, le dossier suspect `junk` et son propriétaire `spy7`.
